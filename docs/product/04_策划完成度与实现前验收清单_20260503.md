## 4. 第一轮实现验收

Slice A 完成标准：

1. 无真实 API key 也能运行。
2. mock model 能参与英雄行动。
3. 英雄和敌人按读条行动。
4. 英雄行动必须通过 action schema。
5. 本地裁判能校验 MP、冷却、目标。
6. 非法 action 有降级或惩罚。
7. 战斗能胜利或失败。
8. 战斗结束能输出 trace。
9. Slice A 中 `REQ-*` 的状态能根据实现结果更新。
10. 每个完成需求都有测试、trace 或日志证据。
11. `ouro --version` 可运行。
12. `ouro play --mock` 不需要 API key。
13. `ouro config show` 不显示 API key 明文。
14. ASCII-safe 战斗主屏可读。
15. 仓库目录骨架存在，每个目录有 README 和 `_rules.md`。

C-Experience 完成标准：

1. `play --mock --delay 0.1` 能显示逐 turn 动作帧，而不是静默等待后输出最终画面。
2. 英雄选择/详情能展示武器、Build、技能、Prompt 策略和上手风险。
3. `--no-animation` 仍保留 turn frame、实时日志和战报。
4. 战报包含技能使用率、普攻占比、主要伤害来源、死亡原因。
5. 默认试玩模式下路线、奖励、商店不静默自动选择。
6. 批量试跑能输出技能使用率、连续普攻、ready skill ignored 等数值指标。

C-GameUI 完成标准：

1. 主菜单、英雄、奖励、图鉴至少 4 类界面使用卡片/图标/面板，而不是纯文本段落。
2. 战斗主屏有低密度场景背景，且不影响核心数值阅读。
3. 每个英雄和 MVP 怪物有动作状态，并能在行动帧中使用。
4. 图鉴有 locked/fog/observed/mastered 卡片状态。
5. Build 面板显示成型阶段、active resonance、near resonance、best next picks。
6. 经验升级能调整 Strategy/Codex/Memory/Prompt edit 至少一种 context 槽位。
7. 战斗主屏默认左英雄、右怪物，中间有技能弹道/命中/格挡效果层。
8. 英雄和 MVP 怪物至少有 4-6 行战斗精灵，不只是短标识或文字动作。
9. 武器显示 `[W:*]` 图标和轮廓，Build 显示 `[SEED]`/`[PAIR]`/`[ONLINE]`/`[HIGH]`/`[LOCK]` 阶段徽章。

这些问题不阻塞第一轮 coding，但需要在进入完整 MVP 前确认：

## 7. 标准对齐 Gate

进入 coding 前必须满足：

| Gate | 要求 |
|------|------|
| GDD Gate | 玩法目标、玩家体验、系统规则、不可做和验收标准明确 |
| Requirement Gate | 本轮需求已写入 `06_需求追踪矩阵_20260503.md` |
| Evidence Gate | 每个需求有测试、trace、日志或试玩记录作为证据类型 |
| Scope Gate | 本轮不做项明确写出 |
| Change Gate | 需求变更必须更新追踪矩阵和设计基线 |

---

## 6. 防跑偏提醒

1. 不要先做排行榜。
2. 不要先做复杂 UI。
3. 不要先接真实模型。
4. 不要让模型决定伤害或掉落。
5. 不要做小队。
6. 不要把游戏做成评测报告生成器。
7. 不要只实现流程对象和 trace，却不给玩家屏幕反馈。
8. 不要把 CLI 风格降级理解为纯文本日志。
9. 不要把战斗主屏做成上下列表或单列日志。
