# Ouro Agent 玩家可感知体验整改规格

> 版本：v0.1  
> 日期：2026-05-04  
> 来源：`docs/player_experience_report_20260504.md`、Trae 备用工作区流程验证、RicHe 当前反馈  
> 目的：把“系统能跑”升级为“玩家能感知、能选择、能复盘”的 CLI 游戏体验合同。

> 延伸规格：CLI 游戏化界面、图鉴卡片、动作资产、Build 胡牌和 context 成长见 `17_CLI游戏化体验美术Build深化规格_20260504.md`。

---

## 1. 核心判断

当前实现方向已经证明战斗引擎、Provider、trace、内容加载都可以成立，但体验风险是：实现者很容易只完成流程对象和最终输出，让产品看起来像接口测试。

本规格新增一条硬规则：

> 任何标记为可玩的流程，都必须在玩家屏幕上呈现“可感知事件”。trace 只能作为复盘证据，不能替代玩家当场看到的反馈。

---

## 2. 全局体验链路

MVP 新手副本必须覆盖完整体验链，而不是只跑一场战斗。

```text
启动游戏
  ↓
主菜单 / Provider 状态
  ↓
选择英雄
  ↓
查看武器、Build、技能、Prompt 摘要
  ↓
配置 Prompt：自动 / 半自动 / 预设策略
  ↓
开始新手副本
  ↓
路线选择
  ↓
战前预告：敌人、风险、推荐 Build 提醒
  ↓
实时自动战斗：动作帧、日志、数值变化、模型决策
  ↓
战斗结算：胜负原因、技能使用、承伤来源、图鉴变化
  ↓
奖励 / 商店 / 休息 / Prompt 调整
  ↓
进入下一节点或失败结算
```

---

## 3. 模式定义

| 模式 | 玩家操作 | 用途 | 默认 |
|------|----------|------|------|
| 自动观战 | 战斗中不输入，只能暂停/加速/查看日志 | 普通试玩、真实模型演示 | 是 |
| 半自动策略 | 战斗外选择策略模板、Prompt 槽、Build 倾向；战斗中不手动选技能 | MVP 最适合的可玩模式 | 是 |
| 手动测试 | 指定 seed、hero、enemy、provider、no-animation | 开发验证 | 否 |
| 全自动批跑 | 路线/奖励自动选择，输出统计 | 数值验证和 CI | 否 |

实现要求：

1. 玩家试玩默认不能静默自动选择路线和奖励。
2. `--auto` 或 batch 命令可以自动选择，但屏幕必须标记为测试/批跑模式。
3. `--no-animation` 只关闭延迟和装饰动画，不能关闭 turn frame 和战斗日志。

## 4. 开始游戏与英雄选择

### 4.1 主菜单必须显示

1. 当前 Provider、model、language、visual mode。
2. 是否 mock，可否无 key 试玩。
3. 最近一次 run 或 trace 路径。
4. 主要命令入口：New Run、Hero Card、Configure Model、Replay、Quit。

### 4.2 英雄选择必须展示

| 字段 | 说明 |
|------|------|
| 英雄短标识 | 如 `[CNDL]`、`[XBOW]` |
| 职业和定位 | 控制、守护、猎手、毒沼、装置、回声 |
| 当前武器 | 展示武器名、档次、核心标签 |
| Build 类型 | 如 Interrupt、Bleed Execution、Poison Attrition |
| 技能组合 | 3 个技能的 MP、CD、用途 |
| 模型策略摘要 | 3 行以内，说明自动战斗倾向 |
| 上手难度 | easy / normal / hard |

验收：

```text
玩家只看英雄选择页，不打开文档，也能判断每个英雄大概怎么玩。
```

## 5. Prompt 与 Build 配置

MVP 不要求自由文本编辑器，但必须给玩家可理解的配置入口。

| 配置项 | MVP 做法 | 延后做法 |
|--------|----------|----------|
| Prompt 风格 | 预设模板三选一：Aggressive / Guarded / Control | 自由编辑多行 Prompt |
| 策略槽 | 选择 1-2 条战术偏好 | 多槽位成长 |
| Build 摘要 | 自动从装备/词条/羁绊生成 | 玩家自定义 Build 名称 |
| 图鉴注入 | 显示本场可注入的已知怪物信息 | 玩家手动排序图鉴知识 |

Prompt 配置页必须明确告诉玩家：

1. 战斗中模型会自动选 action。
2. 本地 judge 才决定伤害、状态、胜负。
3. 玩家此处配置的是“倾向”，不是作弊指令。

## 6. 战斗实时反馈合同

每次英雄或敌人行动后，CLI 必须输出或刷新一次 Battle Frame。

Battle Frame 最少包含：

| 字段 | 说明 |
|------|------|
| tick / turn | 当前时刻和行动序号 |
| actor | 谁行动 |
| action beat | 像游戏动作的短句，不是接口日志 |
| target | 目标是谁 |
| cost | MP、CD、资源变化 |
| impact | 伤害、护盾、治疗、ATB、状态变化 |
| judge | valid/fallback 和本地结算摘要 |
| recent log | 最近 6-10 条事件 |

硬性不通过条件：

1. 战斗只在结束后渲染最终画面。
2. turn hook 只写 trace 或只 sleep，没有屏幕反馈。
3. 日志只存在 trace，玩家屏幕看不到。
4. 英雄行动只显示 action id，没有动作描述和结算后果。

## 7. 动作表现规格

动作表现分为三层，MVP 至少完成前两层。

| 层级 | 内容 | 示例 |
|------|------|------|
| L1 结构化动作行 | action、skill、target、damage、status | `Action: Shadow Sting -> Acolyte | 34 shadow, CRP +1` |
| L2 角色动作短句 | 1 行氛围动作 | `Astia lifts the black candle; the shadow tightens into a needle.` |
| L3 ASCII 微动画 | 2-3 帧可关闭动画 | `CNDL >> shadow >> [k]` |

动作文案规则：

1. 每个英雄至少 3 条通用动作句，3 条技能动作句。
2. 每个怪物家族至少 3 条攻击/吟唱/受击句。
3. 动作句必须短，不超过一屏宽度。
4. 动作句不能改变规则含义，只解释已发生结算。

## 8. 战斗日志与战报

### 8.1 实时日志

实时日志不是 debug log。它必须为玩家解释刚发生了什么：

```text
LOG
> Tick 12 Astia casts Hex Seal. MP 54 -> 36.
> Hex Seal deals 12 shadow to Black Candle Acolyte.
> Black Candle Acolyte gains SLN silence(2).
> Hungry Cultist reaches 80 ATB.
```

### 8.2 战斗结算

每场战斗结束必须输出战报：

| 字段 | 必须性 |
|------|--------|
| result | 必须 |
| duration ticks / hero turns | 必须 |
| killed by / routed by | 失败必须 |
| hero action counts | 必须 |
| skill usage / basic attack ratio | 必须 |
| damage dealt / damage taken top sources | 必须 |
| fallback / invalid action count | 必须 |
| codex unlock / reward | 有则显示 |
| Build note | 建议显示 |

## 9. 副本交互合同

### 9.1 路线选择

路线选择必须显示选项，不允许玩家试玩默认静默选第一个。

```text
ROUTE :: LAYER 2

[1] [M] Hungry Followers       risk: low   reward: gold/xp
[2] [$] Black Candle Merchant  risk: safe  reward: shop, no xp

Choose node (1-2), or q to quit:
```

### 9.2 奖励选择

```text
REWARD

[1] Ash-Steel Blade      weapon   ATK +3, tag: blade
[2] Corrupted Focus      affix    tag: corruption, shield start
[3] Echo Fragment        archive  codex progress +1

Choose reward (1-3):
```

### 9.3 商店与休息

商店 MVP 可以很简，但必须能购买或离开；休息必须改变 run-level HP/MP 或明确说明当前无损耗。

## 10. 数值体验整改原则

数值第一版不追求公平，先追求“能看懂、能打完、能感知差异”。

新增三条红线：

1. 法系/毒系英雄不能因为普攻过低而陷入 20+ 次无意义普攻。
2. 装置/力量英雄不能因为普攻过高导致技能失去存在感。
3. 精英节点不能在新手副本早期用两个机制怪直接封死路线。

第一轮目标：

| 指标 | 普通战 | 精英战 | Boss |
|------|--------|--------|------|
| 英雄行动数 | 4-8 | 6-10 | 8-14 |
| 技能使用率 | >= 35% | >= 40% | >= 45% |
| basic_attack 占比 | <= 60% | <= 55% | <= 50% |
| 真实模型非法/降级 | <= 10% | <= 12% | <= 15% |

## 12. 验收证据

每个体验需求完成时至少提供一种玩家可读证据：

1. 终端截图或完整输出日志。
2. 固定 seed 的 mock 战斗输出。
3. trace + 战报摘要。
4. 批量试跑统计表。
5. 人工试玩记录。

仅有单元测试不够，因为本规格验收的是玩家可感知体验。
