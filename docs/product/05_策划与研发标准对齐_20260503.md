# Ouro Agent 策划与研发标准对齐

> 版本：v0.1  
> 日期：2026-05-03  
> 用途：把外部 GDD / 需求 / 研发标准转成 Ouro Agent 可执行的项目规则。  
> 结论：后续 coding 工具不能只读玩法描述，必须按“需求条目 -> 验收标准 -> 验证证据 -> 追踪矩阵”执行。

---

## 1. 参考来源

| 来源 | 可借鉴点 | Ouro Agent 用法 |
|------|----------|-----------------|
| Unity Learn: Game Design Document | GDD 是活文档，帮助沟通、发现问题、管理范围；应覆盖目标、机制、体验、视觉和开发计划 | 把 GDD 拆为总纲、模块策划、设计基线和验收清单 |
| ISO/IEC/IEEE 29148 | 需求工程应覆盖利益相关方需求、系统需求和软件需求，并关注需求质量 | 每个可实现功能要有需求 ID、来源、验收标准和验证方法 |
| ISO/IEC/IEEE 12207:2026 | 软件生命周期过程覆盖从概念、开发、运行、维护到退役，并兼容敏捷/迭代 | Ouro Agent 采用分阶段 Gate：策划、工程骨架、战斗闭环、MVP 验证 |
| Agile Manifesto | 工作软件、客户协作、响应变化优先 | 第一轮必须交付可运行 mock 战斗，不用文档替代体验 |
| NASA Objective Evidence | 用客观证据证明需求实现，避免只看主观判断 | 每个验收项要绑定测试、trace、试玩记录或截图/日志 |

## 2. Ouro Agent 的 GDD 标准

每个游戏策划模块必须包含：

| 区块 | 要求 |
|------|------|
| 模块目标 | 说明这个模块解决什么体验问题 |
| 玩家体验 | 玩家能看到、选择、感受到什么 |
| 系统规则 | 机器可执行的规则，不只写氛围 |
| 输入输出 | 该模块依赖什么数据，产出什么状态 |
| 不可做 | 明确 MVP 不做什么，防止扩 scope |
| 验收标准 | coding 工具完成后如何判断过关 |
| 关联模块 | 标明依赖和被依赖关系 |
| 一致性引用 | 使用 `02_设计基线与术语表_20260503.md` 的术语和 ID |

当前 G01-G15 已具备基础结构，但要进入实现时，还需要把 P0 模块进一步细化成需求条目。

---

## 3. Ouro Agent 的需求标准

每条可实现需求必须满足：

| 字段 | 说明 |
|------|------|
| Requirement ID | 稳定 ID，例如 `REQ-BTL-001` |
| 来源 | 来自哪个策划模块或 RicHe 决策 |
| 玩家价值 | 这条需求给玩家带来什么体验 |
| 系统行为 | 程序必须做什么 |
| 验收标准 | 可验证的完成条件 |
| 验证证据 | 测试、trace、日志、截图、试玩记录 |
| 优先级 | P0/P1/P2/P3 |
| 实现切片 | Slice A/B/C/D/E/F |
| 状态 | draft/ready/in_progress/done/blocked |

不符合这些字段的内容只能算想法，不能直接进入 coding。

---

## 4. 可执行性分级

| 等级 | 含义 | 是否能交给 coding |
|------|------|------------------|
| E0 想法 | 只有概念或体验描述 | 否 |
| E1 策划 | 有模块规则和边界 | 还不够 |
| E2 需求 | 有需求 ID、系统行为、验收标准 | 可以拆任务 |
| E3 可验证需求 | 有验证方法和证据类型 | 可以实现 |
| E4 可复测需求 | 有测试/trace/seed/mock model | 可以进入自动化验证 |

Ouro Agent 第一轮 coding 必须至少达到 E3；战斗系统、模型行动协议、内容数据必须达到 E4。

---

## 5. 第一轮研发 Gate

进入 Slice A 前必须满足：

| Gate | 标准 |
|------|------|
| GDD Gate | G02、G05、G08、G09、G10 已读，术语和 ID 与设计基线一致 |
| Requirement Gate | Slice A 需求写入 `06_需求追踪矩阵_20260503.md` |
| Test Gate | 明确 mock model、非法 action、MP/冷却、胜负、trace 的验证方法 |
| Scope Gate | 不接真实模型、不做路线/商店、不做排行榜 |
| Evidence Gate | 实现完成后必须留下测试结果或战斗 trace |

---

## 6. 文档到研发的传递格式

coding 工具接任务时，不应只收到“做战斗系统”，而应收到：

1. 读取文件清单。
2. 需求 ID 列表。
3. 本轮不做事项。
4. 验收标准。
5. 验证命令或验证证据要求。

示例：

```text
实现 Slice A:
- 读取 G02、G05、G08、G09、G10
- 完成 REQ-BTL-001 到 REQ-LLM-004
- 不接真实模型，不做商店，不做排行榜
- 验收：mock model 可跑完整战斗，非法 action 被降级，输出 trace
```

## 7. 当前缺口

| 缺口 | 影响 | 处理 |
|------|------|------|
| 模块策划已有，但需求 ID 还不完整 | coding 工具难以逐条验收 | 新增需求追踪矩阵 |
| G02/G05 可执行性较高，G03/G04 仍偏策划 | 第一轮实现应避开 G03/G04 大内容 | Slice A 只做战斗和模型协议 |
| 技术栈未定 | 工程骨架暂不能开 | 等 RicHe 审批 |
| 验证命令未定 | 只能定义证据类型 | 工程建立后补命令 |
| 体验验收还缺试玩模板 | MVP 后补 | 先用 trace 和 mock 测试 |
