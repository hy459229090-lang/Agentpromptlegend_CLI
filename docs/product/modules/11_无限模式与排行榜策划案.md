# G11 无限模式与排行榜策划案

> 状态：v0.1 延后策划  
> 依赖：MVP 可试玩、G09 trace、G10 验证  
> 目的：先预留长期方向，避免 MVP 数据结构完全无法支持后续排行榜。

---

## 1. 模块定位

无限模式和排行榜不是 MVP 功能。它们的价值是让玩家用不同模型、Build 和 Prompt 比较长期表现，但必须建立在稳定单机玩法和本地 trace 之上。

---

## 2. 无限模式核心

无限模式是连续推进的副本：

1. 层数不断增加。
2. 敌人强度递增。
3. 奖励品质递增。
4. 商店和事件间隔出现。
5. 死亡后结算本次成绩。

---

## 3. 排行榜成绩字段

后续排行榜至少需要：

| 字段 | 说明 |
|------|------|
| 层数 | 最核心成绩 |
| 击败 Boss 数 | 判断阶段推进 |
| 用时 | 可选排名维度 |
| 模型名 | 玩家自选模型 |
| provider 类型 | 可脱敏记录 |
| Build 摘要 | 不含完整私密 Prompt |
| seed / 规则版本 | 判断是否同赛季 |
| 非法行动率 | 防止纯靠模型乱试 |
| token / 成本摘要 | 可选展示 |

---

## 4. 隐私与上传边界

排行榜上传默认不能包含：

1. API key。
2. 完整英雄 Prompt。
3. 原始模型响应全文。
4. 本地路径。
5. 用户身份信息。

可上传：

1. 脱敏成绩。
2. 规则版本。
3. 模型名或玩家自填模型标签。
4. Build 标签摘要。
5. 统计指标。

---

## 5. 公平性约束

排行榜必须分赛季或规则版本：

1. 不同规则版本不能直接比较。
2. 不同内容版本不能直接比较。
3. mock model 成绩和真实模型成绩分开。
4. 自定义副本成绩不进入官方榜。

---

## 6. MVP 需要预留什么

MVP 不做排行榜，但需要预留：

1. 规则版本字段。
2. seed 字段。
3. trace 摘要字段。
4. 模型名字段。
5. Build 摘要字段。

---

## 7. 不可做

1. MVP 不做在线上传。
2. 不为了排行榜牺牲单机游戏性。
3. 不上传原始 Prompt 和原始 trace。
4. 不把不同模型混成一个绝对能力排行。

---

## 8. 验收标准

进入该模块实现前必须满足：

1. 单机 MVP 可试玩。
2. 本地 trace 稳定。
3. 无限模式规则有版本号。
4. 有明确脱敏字段。
5. RicHe 再次确认上传和排行榜边界。
