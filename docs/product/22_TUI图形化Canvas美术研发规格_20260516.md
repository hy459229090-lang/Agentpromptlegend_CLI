# TUI 图形化 Canvas 美术研发规格

> 日期：2026-05-16  
> 状态：P0 实施规格  
> 来源：用户反馈、研发/美术/策划三方复盘  
> 目标：把 Ouro Agent 的 TUI 从字符拼接升级为终端低分辨率图形画布。

---

## 1. 结论

当前 `21_像素风TUI美术研发边界与需求规格_20260516.md` 的 pixel panel 可保留为 ASCII fallback，但它不能作为最终美术目标。

新的方向是：

> 暗黑终端低像素图形剧场。ASCII 是兼容底线，Unicode block / ANSI 色层才是推荐观感目标。角色、怪物、武器、弹道和状态条都应作为低分辨率图形资产绘制，而不是继续在 `screens.py` 中拼接标点。

---

## 2. 技术边界

| 层级 | 用途 | 字符/能力 | 优先级 |
|------|------|-----------|--------|
| ASCII fallback | CI、PowerShell、日志、no-color | `# . : = - / \ | []` | P0 必须 |
| Unicode block canvas | 默认推荐观感 | `█ ▓ ▒ ░ ▀ ▄ ▌ ▐` | P0 |
| Unicode fine pixel | 精灵、弹道、破损、雾面 | `▖ ▗ ▘ ▙ ▚ ▞ ▟` | P1 |
| ANSI theme | HP/MP/ATB、危险、反制、高潮 | 16/256/truecolor，可关闭 | P1 |
| Braille texture | 毒雾、星尘、档案噪声 | Braille 点阵 | P2，可选 |
| Bitmap sprite renderer | 最佳交互路径 | Kitty Graphics、iTerm2 inline image、SIXEL | P0 垂直切片，P1 扩展 |

约束：

1. 默认输出必须 ASCII-safe。
2. Unicode/color 只能增强观感，不能承载唯一语义。
3. 核心画布 glyph 必须是单宽字符。
4. 中文只进入文本层，不进入像素画布层。
5. `--no-animation` 可以去掉延迟，但不能去掉 turn frame、动作节拍和战斗日志。
6. TUI 不修改战斗规则，所有伤害、胜负、掉落仍由本地引擎决定。
7. Bitmap 图形能力必须通过 terminal capability 自动检测；缺失时降级到 Unicode cell sprite，再降级到 ASCII。
8. Bitmap renderer 是最佳互动体验，不是唯一可运行路径；mock、CI、pipe、no-color 和 no-animation 必须继续稳定。

---

## 3. 用户旅程目标

玩家运行 `ouro play --mock` 时，应经历以下感受：

1. 第一眼看到左英雄、右怪物、中间效果 lane，而不是报告页。
2. 每个 turn 都能看见 SELECT、IMPACT、JUDGE 三个节拍。
3. 英雄像一个正在执行策略的 Agent，有局势台词和意图/风险/契合提示。
4. 怪物不是血条目标，而是有 idle、attack/cast、hit、break、death 的剪影变化。
5. HP/MP/ATB 不是字段堆叠，而是图形条 + delta + 阈值提示。
6. 武器与 Build 不是装饰字段，而是解释“为什么英雄会这样打”的图形卡。

## 3.1 2026-06-15 现代 CLI/TUI 对标补充

本轮视觉目标以成熟终端产品的方法为参照，但不复刻任何品牌、图标或专有界面。
Ouro 的目标不是“像某个工具”，而是把它们证明有效的交互语言转译成终端游戏。
已核对的公开来源：Claude Code [statusline](https://docs.anthropic.com/en/docs/claude-code/statusline) / [output styles](https://docs.anthropic.com/en/docs/claude-code/output-styles)、[Posting](https://posting.sh/)、[superfile](https://github.com/yorukot/superfile)、[btop](https://github.com/aristocratos/btop)、[Rich Live](https://rich.readthedocs.io/en/latest/live.html)、[Textual](https://textual.textualize.io/)。

| 对标 | 可借鉴能力 | Ouro 转译 |
|------|------------|-----------|
| Claude Code Ultracode / workflows | 阶段列表、运行进度、可暂停/停止/钻取子任务 | 战斗导演拆成 `THREAT -> SELECT -> IMPACT -> JUDGE -> MEANING`，每个阶段有可见帧、当前焦点和结果 |
| Claude Code status line | 底部持久状态线，展示 context、成本、时间和工作目录等会话状态 | 常驻 `Echo Cost`、`Read Echo`、`Spoken Echo`、`Ritual Time`、Provider、seed、danger rail，但优先级低于 HP/MP/ATB |
| Posting | 键盘优先、jump mode、命令面板、自动补全 | run 内路线/奖励/商店/休整/事件共享 Nav、Focus Rail 和 Command Rail，未来支持跳转与命令面板 |
| superfile | 多面板、预览区、焦点态、主题化 | Hero/Build/Codex/Route/Reward 采用卡片、预览、焦点轨和一致主题 token |
| btop | 高密度实时 HUD、低闪烁刷新、图形符号 fallback | 战斗主舞台使用 Canvas、局部刷新、同步输出策略和 ASCII/Unicode glyph fallback |
| Rich Live / Textual | live display、alternate screen、组件化 TUI、终端/浏览器双运行潜力 | 第一阶段保留 dependency-free ANSI renderer；第二阶段评估 Rich Live 或 Textual app shell |

### 可执行设计原则

1. 默认体验必须动起来：模式选择、战斗、奖励、路线和关键状态变化都要有焦点态或过场帧。
2. 动效是信息架构，不是装饰：每个动画阶段必须回答“当前焦点、风险、结果、下一步”。
3. 局部刷新优先：默认 TTY 体验应减少全屏滚动和闪烁；日志/CI/管道输出仍可走静态帧。
4. `--no-animation` 不等于无画面：它只移除延迟、闪烁和微动画，必须保留阶段帧和日志。
5. Rich/Textual 迁移不能污染引擎：战斗规则、Provider、RunState、trace schema 不因 TUI shell 改变。
6. 中文与 ASCII fallback 同等验收：所有新 HUD、命令轨、焦点轨必须有中英文和 80/100/120 宽度证据。

### 3.2 2026-06-15 Rich/Textual Spike 结论

`venv312/bin/python scripts/tui_shell_spike.py` 是当前二阶段 TUI shell 的可复验评估入口。它只检查候选 shell、输出 dry-run contract，不改变默认 gameplay。

当前结论：

1. `current-ansi-renderer` 保持默认路径；它已经覆盖局部刷新、alternate screen、ASCII-safe fallback、`--no-animation` 和确定性快照。
2. `rich-live` 作为第一个可选 adapter 原型：先包裹现有 `PresentedFrame` 字符串，验证 live refresh、status line、CI/pipe 降级和截图证据，再决定是否加 optional dependency。
3. `textual-app-shell` 暂不进入默认路径：等键盘路由、headless snapshot、安装体积和无障碍 fallback 都有证据后再评估。
4. `pyproject.toml` 不新增 Rich/Textual 运行时依赖；mock-first 安装和 release check 不能因为二阶段探索变重。
5. 任何 shell adapter 必须遵守 `Engine Event -> BattleFrame -> BattleScreenModel -> PresentedFrame -> ShellAdapter`，并且 `ShellAdapter.close()` 只能恢复终端状态，不能修改 RunState。

### 3.3 2026-06-15 战斗动效审美纠偏

本次用户反馈指出：当前动画“确实在动”，但“不好看”。根因不是动画数量不足，而是策划验收把“有阶段、有 HUD、有说明文字”误当成“有游戏演出”。后续不再继续堆叠 `TITLE / PHASE`、rail、overlay、pulse 这类文字型 HUD，必须回到战斗舞台本身。

Product Design brief：

- 产品：Ouro Agent 的默认 CLI/TUI 战斗观战体验。
- 目标：玩家第一眼看到的是暗黑终端低像素战斗舞台，而不是动态文档、日志表格或状态说明书。
- 参考方法：学习现代终端产品的局部刷新、焦点态、状态线和键盘流；学习游戏战斗演出的镜头节奏、hit stop、位移、缓动、数值跳字和角色 pose 变化。
- 交互级别：默认 TTY 全动态；`--no-animation` 保留确定性分镜帧；ASCII fallback 可读但不作为审美上限。
- 角色资产：默认推荐体验不允许基于 ASCII 线条小人；角色和怪物必须来自 Ouro 自有视觉元素的 sprite atlas。ASCII 只做兼容 fallback。

#### 3.3.1 当前失败诊断

| 问题 | 表现 | 为什么不好看 |
|------|------|--------------|
| 文字层过重 | 每个状态都有标题、相位条、overlay、pulse、FOCUS/RISK/NEXT | 画面在解释自己，玩家没有看到动作本身 |
| 舞台层被挤压 | 真正的左右角色、弹道、命中反馈被大量 HUD 包围 | 视觉焦点分散，战斗不像主画面 |
| 动效语法重复 | mode、encounter、battle result、reward reveal 都长得像同一套状态面板 | 缺少游戏事件的情绪差异 |
| 相位名替代镜头 | `SELECT/WINDUP/TRAVEL/IMPACT/JUDGE` 更多出现在标题，而不是体现在角色和效果 lane | 玩家需要读字才能理解动作 |
| 奖励了错误验收 | 测试主要检查关键字、宽度、相位名和负向泄漏 | 没有检查构图、留白、角色 pose、命中停顿和运动连续性 |

#### 3.3.2 新设计原则

1. **舞台优先**：默认战斗帧的最大视觉面积必须给左英雄、右敌人和中心 effect lane；HUD 只能服务舞台，不得压过舞台。
2. **少字强反馈**：核心动作通过位移、缓动、反白、血条跳变、伤害数字、pose 改变表达；说明文字减少到短标签。
3. **每个 phase 改变画面，不只改标题**：
   - `idle`：双方站稳，低密度背景呼吸。
   - `windup`：行动方前压或武器/法器抬起，目标侧出现 reticle。
   - `release`：中心 lane 出现弹道/斩击/法印。
   - `hit_stop`：目标短暂停顿、反白或破损，伤害数字贴近目标侧。
   - `settle`：血条与状态落定，pose 回到新常态。
4. **固定构图**：同一场战斗中角色列和中心 lane 位置不跳动；只在格内替换 pose、效果和数值。
5. **有限 HUD**：默认 battle frame 只允许一个顶部 status line、一个舞台、一个短 action strip、一个最近 2-3 条 log；长分析进入战报或 `--no-animation` 日志。
6. **颜色/Unicode 增强但不替代设计**：颜色和闪烁只能做强调，不得作为主要动效。主要动效必须来自 sprite 逐帧变化、中心 effect lane 运动和 HUD 数值落点。
7. **自有角色元素**：Astia 不是 `. ^ /|` 小人，而是“黑烛兜帽、烛杖、暗焰面罩”的低分辨率角色符号；敌人也必须有家族剪影、破损、残骸和图鉴剪影。
8. **GIF 式时间轴**：默认 TTY 动画不是 3 个状态快照，而是 8-12fps 的连续短 timeline；每次技能至少 8 帧，包含 anticipation、motion、impact、recovery。

#### 3.3.3 Combat Stage V2 画面合同

默认 `ouro play/run --mock --unicode` 的核心战斗动画应从“状态面板动画”改为“sprite 时间轴动画”。它应该像终端里的低分辨率 GIF：同一个舞台区域内连续刷新角色、弹道、命中和恢复帧，而不是只切换标题或闪一下颜色。

```text
--------------------------------------------------------------------------------+
| EMBER CRYPT  T009  ASTIA acts        Provider mock  Seed 2                     |
|                                                                                |
|        HERO                         EFFECT LANE                      ENEMY     |
|       ▄██▄                          ░░ seal ember ░░                 ▐▓▓▌     |
|      ▐█c █▌                 . . .   --==*==>   . . .                ▐█k█▌     |
|       ▀██▀                          HIT STOP  -16 HP                  ▀▓▀      |
|   HP ███████░ 82/100                                             HP ███░░ 34/70|
|   MP ████░░░ 54/72       [W:STF] Hex Seal -> k       ATB █████░  CHANT CUT     |
|                                                                                |
|  ACTION  windup -> release -> HIT STOP -> settle                               |
|  LOG     Seal breaks the chant. Local judge: valid, -16 HP, silence(1).        |
+--------------------------------------------------------------------------------+
```

必须避免：

1. 首屏出现超过 3 行解释性 `FOCUS/RISK/NEXT` 文案。
2. 每帧都用大标题重复 `PHASE`。
3. 角色舞台被上下文、成本、trace、长诊断挤到次要位置。
4. 用“动画存在”替代“动作可读”。
5. 把人物画成 ASCII 线条小人后再加颜色、闪烁或反白。
6. 只用 `HIT FLASH`、`PULSE`、`CAMERA` 等文字描述冒充动效。

#### 3.3.4 Sprite Atlas 与 Timeline 合同

默认推荐体验必须引入 Ouro 自有角色资产结构：

| 资产层 | 要求 |
|--------|------|
| `SpriteAtlas` | 按角色/怪物/效果存放命名帧；帧是宽高固定的 cell matrix，不是自由文本段落 |
| `ActorSprite` | 每个 actor 至少有 `idle_a/idle_b/windup_1/windup_2/release/hit/heavy_hit/break/death` |
| `EffectSprite` | 每个技能至少有 `spark_1/trail_1/trail_2/impact_1/impact_2/dissolve` |
| `AnimationTimeline` | 每个动作由 8-12 个 frame key 组成，含 duration、actor pose、effect offset、damage pop offset、screen shake |
| `Renderer` | 固定舞台区域内 compositing，支持局部刷新；不改变 BattleState |

Astia 的 P0 视觉元素：

| 元素 | 设计锚点 |
|------|----------|
| 轮廓 | 兜帽剪影 + 黑烛胸灯 + 短杖 |
| 主色/灰阶 | 深影主体、亮烛芯、暗焰边 |
| idle | 烛火轻微起伏，兜帽稳定 |
| windup | 烛杖抬起，烛芯变亮，身体前压 |
| release | 烛芯拉成长线，法印从杖端脱出 |
| hit/recovery | 烛火回落，兜帽恢复低姿态 |

Hungry Cultist / Black Candle 敌人的 P0 视觉元素：

| 元素 | 设计锚点 |
|------|----------|
| 轮廓 | 瘦长身体、缺口头部、烛/钩刃家族符号 |
| telegraph | 身体后仰或烛芯膨胀，不只是 `charge 33%` 文本 |
| hit | 轮廓破口、暗焰碎片、短暂停顿 |
| break/death | 咏唱环断裂或残骸坍缩，进入 codex silhouette |

Hex Seal 的 P0 timeline：

| 帧 | 时间 | 舞台变化 |
|----|------|----------|
| 1 | 70ms | idle，双方轻微呼吸，effect lane 空 |
| 2 | 70ms | Astia 前压，烛杖抬起，目标出现 reticle |
| 3 | 60ms | 烛芯拉亮，法印在英雄侧生成 |
| 4 | 50ms | 法印向中线移动，trail 拉长 |
| 5 | 50ms | 法印接近敌人，敌方 telegraph 被压住 |
| 6 | 90ms | hit stop，敌方反白/破损，`-HP` 跳字贴近目标 |
| 7 | 70ms | 血条和状态落定，`CHANT CUT`/沉默短标签出现 |
| 8 | 80ms | 双方恢复新 pose，effect dissolve，action strip 收束 |

#### 3.3.5 全量资产优先与冒烟播放切片

P0 验收口径不是“做出一个 Astia / Hex Seal 漂亮案例”。完整资产生产必须覆盖当前 MVP 的 6 名英雄、全部敌人、18 个技能、15 件物品、12 个 affix、5 个 resonance、Ember Crypt 场景/节点类型和 UI 状态。Astia / Hex Seal 只作为播放链路的冒烟切片，用来验证 renderer、timeline、hit stop 和 fallback 是否成立；它不能单独让资产需求或图形战斗目标标为完成。

进入实现前必须先有全量 `AssetManifest`：

1. 每个当前 content ID 都有对应 asset 条目或显式继承关系。
2. 每个条目都有 ImageGen brief、QA 状态、frame metadata、anchor、duration 和 fallback cell ID。
3. `runtime_enabled: true` 只允许用于 `qa_passed` 且本地文件存在的资产。
4. 缺少 bitmap 的内容必须先有 Unicode/ASCII fallback timeline，不能退回普通文字箭头。
5. 后续新增 content 时，如果没有资产条目，不能被标为 release-ready。

| 项 | 选择 |
|----|------|
| 命令 | `ouro --lang en play --mock --seed 2 --hero astia --unicode --color always --no-trace --content-dir content` |
| 英雄 | Astia / Shadow Apprentice |
| 技能 | Hex Seal |
| 敌人 | Hungry Cultist 或 Black Candle Acolyte |
| 分镜 | 8 帧 timeline：idle -> windup -> seal_spawn -> travel_mid -> travel_near -> hit_stop -> settle -> recover |
| 必须可见 | 左英雄、右敌人、中心法印弹道、目标 reticle、hit stop 反白/破损、`-HP` 跳字、敌方 pose 破损、血条跳变、`CHANT CUT`/沉默结果 |
| 禁止 | 不能用 ASCII 线条小人、不能只加颜色/闪烁、不能用大段说明文字替代角色帧 |
| 不改内容 | BattleState、TurnRecord、provider result、trace、伤害、状态、胜负、奖励 |
| 完成限制 | 该切片只证明播放链路；只有全量资产覆盖、QA gate、fallback 和 evidence 都完成后，相关 REQ 才能标 done |

#### 3.3.6 新验收标准

测试不再只检查相位名，而要检查画面合同：

1. 每个 keyframe 必须包含左右 actor 区和 center effect lane。
2. 默认 Unicode/color 路径必须使用 sprite atlas 帧，不得使用 `. ^ /|` 这类 ASCII 线条小人作为角色主体。
3. 一次技能 timeline 至少 8 帧；相邻帧必须在 actor pose、effect offset、damage pop、HUD delta 中至少一项有实际变化。
4. `windup/release/hit_stop/settle` 至少有 3 处可见差异：pose、effect lane、target/damage/HUD。
5. `hit_stop` 帧必须有目标侧伤害跳字和短暂停顿标记，但不能把长说明塞进 HUD。
6. 80/100/120 列稳定，actor columns 不跳位。
7. 中文 Unicode 不泄漏英文相位名；英文 ASCII fallback 仍可读。
8. `--no-animation` 保留压缩分镜帧，但不输出 live chrome 或微动画 ANSI。
9. PTY 证据必须包含 ANSI 局部刷新、hit-stop 帧、伤害跳字、静态战报后继输出；no-animation 证据必须无 ANSI。

### 3.4 2026-06-17 Bitmap Sprite Renderer 实施计划

用户确认概念图方向后，Ouro 的图形化战斗目标从“Unicode block canvas 为上限”升级为“bitmap sprite 优先、Unicode cell sprite fallback、ASCII 兜底”。详细批次见 `docs/planning/OuroAgent_终端图形战斗舞台实施计划_20260617.md`。

执行口径：

1. `ouro doctor graphics` 先交付终端能力检测，解释当前环境能否使用 iTerm2、Kitty、SIXEL 或只能 fallback。
2. 先交付全量 `AssetManifest` 和开发期生图流程：当前 6 英雄、全部 MVP 敌人、18 技能、15 物品、12 affix、5 resonance、场景和 UI 状态都必须登记资产状态。
3. ImageGen 只用于开发期生产候选资产；运行时只能读取 repo 内 QA 通过的本地资产，不联网生成图片。
4. `SpriteAtlas` 和 `AnimationTimeline` 覆盖全量内容；Astia、Black Candle Firekeeper、Hex Seal 只能作为冒烟播放切片，不是完成范围、不是资产范围、也不是验收上限。
5. `RendererBackend` 至少包含 Unicode cell renderer 和一个 bitmap writer；不支持 bitmap 时不得失败。
6. 默认 `--graphics auto` 优先选择 bitmap；非 TTY、CI、pipe、`--no-animation` 使用 deterministic fallback。
7. 证据必须包含 bitmap 或模拟 bitmap filmstrip、Unicode fallback filmstrip、no-animation log。
8. 概念图只作为方向，不直接作为游戏资产；正式资源必须小尺寸、透明背景、有稳定 anchor，并能缩放到终端 stage。

资产目录口径：

1. runtime 图片资产进入 `content/assets/`，并带 `README.md`、`_rules.md`、`manifest.yaml`。
2. Python 代码只保存加载、metadata、renderer 和 fallback 逻辑，不把大批图片硬编码进 `src/`。
3. 每个资产条目必须记录来源 brief、content ID、frame ID、anchor、duration、QA 状态和 fallback cell ID。
4. 未通过 QA 的生成图不得被 runtime 读取。

## 5. 美术规格

### 5.1 人物

P0 每个英雄至少有：

1. ASCII fallback sprite。
2. Unicode block sprite。
3. idle / attack / skill / defend / hit / low / victory / defeat 的等价姿态。
4. 职业锚点：
   - Astia：兜帽、黑烛、火点。
   - Norn：宽盾、重心低。
   - Vela：前倾、弩箭横向。
   - Mirel：瓶形、雾块。
   - Korr：齿轮、背箱。
   - Sera：断铃、声波弧。

### 5.2 怪物

P0 每个 MVP 怪物家族至少有：

1. idle / attack / skill / hit / break / low / death。
2. 家族剪影语法：
   - Hungry Cultist：瘦长、缺口、钩刃。
   - Black Candle：烛芯、黑火、仪式环。
3. 蓄力、破防、死亡必须改变轮廓，而不是只改文字。

### 5.3 战斗画面

P0 战斗主屏必须：

1. 左英雄、右怪物、中间效果 lane。
2. 中间 lane 使用块面弹道，而不是纯文本箭头。
3. 行动结果靠近目标侧显示 `-HP`、`BREAK`、`SLN`、`MISS` 等短标签。
4. ACTION 信息高于 Build、Echo、Log。
5. 反制窗口、错失窗口、高潮击杀有独立视觉 tone。

### 5.4 武器图鉴

P0 武器仍保留 `[W:*]` 产品识别码，同时补充：

1. icon：短标识。
2. silhouette：一行轮廓。
3. card art：3-5 行块面资产。
4. Build Before -> After 与 AI 行为影响说明。
