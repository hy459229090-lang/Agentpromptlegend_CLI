## 当前策划结论

| 项 | 结论 |
|----|------|
| 游戏类型 | 命令行 AI 肉鸽 |
| 风格 | 严肃暗黑 |
| 玩家定位 | 会使用命令行、愿意调 Prompt、喜欢构筑与观战的人 |
| 核心乐趣 | 配置英雄 Agent，然后看它在战斗中自动决策 |
| 战斗控制 | 战斗中玩家不可操作 |
| 战斗机制 | 读条制；下一阶段升级为每场战斗一个 BattleLLMSession，英雄行动时发送 turn delta |
| 结算方式 | 模型只决定 action，本地引擎结算结果 |
| MVP 形态 | 单机、单英雄、新手副本、mock model 可跑 |
| 后续扩展 | 无限模式、排行榜、玩家模型对战 |
| 当前实现 | Cursor 已推进 Slice 0/A/B、双语 UI、真实 Provider adapter；下一阶段优先 C0 Session + C1 Build/UI |
| 当前体验整改 | 下一轮优先 C-Experience + C-GameUI：实时战斗反馈、左右对战图形化主屏、角色/怪物精灵帧、武器/Build 图标、战报、英雄/Build/Prompt 配置、卡片图鉴、场景背景、Build 胡牌和 context 成长 |
| 发布形态 | GitHub 仓库 + 命令行安装 + mock/openai/anthropic/openai-compatible Provider |

## 跨文件一致性规则

1. 所有玩法概念以 `02_设计基线与术语表_20260503.md` 为准。
2. 所有模块都必须使用同一套动作类型、节点类型、装备档次、Session 名称。
3. 文件中出现新增术语、ID 前缀、节点类型、装备档次时，必须同步更新设计基线。
4. coding 工具实现前必须先确认模块策划案的“不可做”和“验收标准”。
5. 第一轮实现前必须读取 `04_策划完成度与实现前验收清单_20260503.md`。
6. 可进入 coding 的需求必须写入 `06_需求追踪矩阵_20260503.md`。
7. 完成实现时必须补充测试、trace、日志或试玩记录作为客观证据。
8. 美术/TUI 设计必须同时满足 ASCII-safe、Unicode-enhanced 和 no-color 三种模式边界。
9. Provider 接入不得明文保存 API key。
10. 代码目录必须按 `08_代码目录与文件摆放规划_20260503.md` 分类，并保持每个目录的 README 和 `_rules.md`。
11. 玩家可玩体验必须满足 `16_玩家可感知体验整改规格_20260504.md`，trace 不能替代屏幕反馈。
12. CLI 游戏化体验必须满足 `17_CLI游戏化体验美术Build深化规格_20260504.md`，ASCII-safe 不能被当成纯文本日志上限。
13. 战斗图形化必须满足 `art/08_战斗界面图形与动作分镜_20260504.md`，默认战斗主屏不得退化为文字日志或上下列表。
