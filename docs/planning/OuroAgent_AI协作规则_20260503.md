## 2. 产品边界

Ouro Agent 第一阶段必须遵守：

1. 目标是先做一个好玩的单机 CLI 肉鸽，不是先做评测平台。
2. MVP 只做单英雄，不做小队系统。
3. 战斗采用读条制；下一阶段采用每场战斗一个 BattleLLMSession，英雄行动时发送 turn delta。
4. 玩家只在战斗外操作：选关、商店、装备替换、Build 调整、英雄 Prompt 调整。
5. 战斗中玩家不能直接选择技能或目标，只能观看战斗反馈。
6. AI 决定行动，游戏引擎决定结果。
7. 严肃暗黑风格优先，不做轻松卖萌风格。
8. GitHub 可安装、mock 试玩、Provider 配置是 MVP 产品化要求。
9. 无限模式、排行榜、玩家模型对战是后续扩展，不进入第一版 MVP。

## 3. 架构硬规则

| 规则 | 要求 |
|------|------|
| 结算确定性 | 伤害、命中、状态、冷却、金币、经验必须由本地规则引擎计算 |
| AI 不可裁判 | 模型不能直接宣布造成多少伤害、获得什么奖励或是否胜利 |
| Action 结构化 | 战斗结算只能读取结构化 action，不读取自由文本 |
| Schema 版本化 | 模型行动协议、存档、内容数据需要有版本号 |
| 数据驱动 | 英雄、技能、装备、怪物、副本尽量用结构化数据定义 |
| 可复测 | 核心战斗必须支持固定 seed 和 mock model |
| 可降级 | 模型输出错误必须有修复、降级、惩罚和日志记录 |
| 可观察 | 每场战斗必须保存关键 trace，便于调试和复盘 |
| 可安装 | 第一轮工程必须能通过命令行安装和启动 |
| 可配置 | Provider、model、base_url、api_key_env 必须通过 CLI 配置 |
| Session 可复盘 | BattleLLMSession 必须记录 session id、static context hash 和 turn delta |

## 4. LLM 使用规则

模型可以做：

1. 根据战况选择行动。
2. 输出给玩家看的动作描述。
3. 引用已解锁图鉴进行战术分析。
4. 在传奇装备允许的有限选项里选择适配效果。
5. 根据玩家 Prompt 表现不同战斗风格。
6. 在同一 BattleLLMSession 内基于已发生行动形成战术连续性。

模型不能做：

1. 虚构不存在的技能、装备、目标、状态。
2. 自行决定伤害数值、掉落、胜负和奖励。
3. 读取未解锁图鉴信息。
4. 绕过冷却、法力、道具数量和行动规则。
5. 用自然语言替代结构化 action。
6. 借 Session 记忆访问未解锁图鉴或隐藏状态。

模型输出失败时：

| 失败类型 | 处理 |
|----------|------|
| JSON 可修复 | 修复后执行，记录瑕疵 |
| 意图可读但结构错误 | 降级执行，降低效果 |
| 不可读 / 非法行动 | 拒绝行动，改为普通攻击、犹豫或读条惩罚 |

## 5. 战斗系统规则

第一版战斗系统必须先跑通最小闭环：

1. 至少 1 名英雄、2 种敌人、3 个技能。
2. 支持 HP、MP、读条、冷却、基础状态效果。
3. 支持普通攻击、技能、防御、观察这几类动作。
4. 支持敌人规则 AI，不要求敌人调用模型。
5. 支持战斗胜负判定和战斗日志。
6. 支持 mock model 自动跑完一场战斗。

不要在战斗闭环完成前实现：

1. 大量装备内容。
2. 随机副本生成。
3. 在线排行榜。
4. 玩家模型对战。
5. 复杂剧情系统。

## 6. 内容设计规则

内容系统必须服务构筑和观战，而不是堆数值。

| 内容 | 规则 |
|------|------|
| 英雄 | 每个英雄必须有默认战斗倾向和技能差异 |
| 技能 | 必须写清消耗、冷却、目标规则、标签和效果 |
| 装备 | 分普通、英雄、传奇三档；传奇必须限制自由度 |
| 词条 | 必须能影响行为、数值或羁绊，不能只写氛围文案 |
| 羁绊 | 必须由有限标签触发，不能靠玩家自由声明 |
| 怪物 | 必须有读条速度、技能、弱点、图鉴阶段 |
| 副本 | 必须有路线选择和风险收益差异 |
| Build | 必须有明确 archetype、核心标签、策略倾向和 UI 展示 |
| Buff/Debuff | 必须有统一 status ID、短名、类型、效果和显示规则 |
| 怪物家族 | 必须有 family ID 和 I/II/III 三档扩展方向 |

ID 使用稳定英文 snake_case；展示名可以使用中文。

## 7. CLI / TUI 表现规则

CLI 表现必须让玩家愿意观战。

最低要求：

1. 展示英雄和敌人的 HP / MP / 读条。
2. 展示模型正在选择行动、选择了什么、为什么。
3. 展示技能动作、目标、伤害、状态变化。
4. 展示冷却和法力不足导致的行动失败。
5. 展示战斗后奖励和构筑变化。

风格规则：

1. 暗黑、克制、清晰。
2. 不使用大段解释性旁白淹没战斗。
3. 不牺牲可读性追求视觉花哨。
4. 动画必须可关闭或可加速，方便测试。

---

## 8. 测试与验证规则

任何进入实现阶段的核心模块都必须有验证方式。

| 模块 | 最低验证 |
|------|----------|
| 战斗引擎 | 单元测试：伤害、冷却、MP、状态、胜负 |
| Action Validator | 合法、非法、可修复、不可修复样例 |
| Prompt Composer | 快照测试或 golden prompt |
| Session 管理 | Run/Battle/Turn trace 可保存和重放 |
| 内容数据 | schema 校验和引用完整性检查 |
| CLI 表现 | 至少一次人工试玩记录或截图/日志 |

模型 API 测试不能作为默认单元测试依赖；默认测试必须能用 mock model 跑。
